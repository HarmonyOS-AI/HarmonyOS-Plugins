# 域：全局 UI 适配

覆盖与多设备布局同时放大的全局 UI 风险：RTL、长文本、深浅色、字体缩放和无障碍。外接键鼠焦点、手写笔、智慧屏专属交互、穿戴和画中画不属于本域。

## 症状定位

| 症状 | 检查方向 |
|---|---|
| 阿拉伯语/希伯来语下左右关系错误 | RTL 与方向无关属性 |
| 大屏限宽后长文案反而截断 | 长文本膨胀与容器约束 |
| 深色模式下自定义颜色不可读 | 资源限定词与自定义色 |
| 系统放大字体后按钮、Tab 或弹窗破版 | `fp`、固定高度与换行策略 |
| 分栏后读屏顺序不符合视觉顺序 | 组件结构和无障碍分组 |

这些问题大多不能由当前静态规则可靠判定。只在工程实际涉及对应语言、主题或无障碍要求时检查，不为所有任务强制扩张范围。

## RTL 与长文本

### 使用方向无关表达

优先使用 `start/end` 语义，避免把布局写死为 `left/right`：

| 避免 | 推荐 |
|---|---|
| `padding({ left: 16 })` | `LocalizedPadding` 的 `start` |
| `margin({ right: 8 })` | `LocalizedMargin` 的 `end` |
| `position({ x: 0 })` | `RelativeContainer` 的 `start/end` 锚点 |

`LocalizedPadding` / `LocalizedMargin` 的字段和值类型必须按当前 SDK 核实；不要因为普通语言下能编译就认为 RTL 正确。品牌标识、数字、公式和不应镜像的媒体图标要单独保持 LTR 或原方向。

### 长文本与大屏限宽

大屏布局常通过 `GridCol span/offset` 限制阅读宽度，实际内容区不一定比手机更宽。检查按钮、标题、Tab 和弹窗时至少覆盖一种长文本或膨胀语言。

空间不足时依次考虑：允许折行、调整容器、隐藏低优先内容、改变结构；不要优先缩小字号。具体布局策略见 [size-layout.md](size-layout.md)。

## 深浅色

系统颜色资源会随模式切换，自定义颜色需要在 `base` 与 `dark` 等资源目录中提供同名键：

```text
resources/
  base/element/color.json
  dark/element/color.json
```

只使用系统颜色资源的页面无需重复截图；存在自定义颜色、图片或动态主题时，视觉验证应覆盖浅色和深色。切换应用内主题后还要验证回到“跟随系统”的路径。

## 字体缩放

用户字体缩放会放大 `fp` 文字。重点检查固定高度按钮、标签、Tab、弹窗标题和分栏后的窄内容区：

- 文字容器允许合理换行并给出高度弹性；
- 重要文本不能因 `maxLines(1)` 和固定高度组合被裁掉；
- 资源字号和运行态主题值不能只靠静态字面量规则判断；
- 手机和大屏都要验证，不能假设大屏空间足够。

文本容器和空间取舍见 [size-layout.md](size-layout.md#文本容器约束)。

## 无障碍结构

读屏顺序跟随组件树，而不是视觉坐标。把手机单列改成大屏分栏时，保持语义分区和视觉顺序一致；不要为了摆放方便把右栏组件提前声明。

常用属性：

| 属性 | 用途 |
|---|---|
| `accessibilityText` | 为纯图标或非文本控件提供可理解名称 |
| `accessibilityLevel` | 排除装饰元素，避免无意义朗读 |
| `accessibilityGroup` | 将分栏中的语义区域组织成可跳过的整体 |

无障碍属性名和允许值以当前 SDK 为准。涉及读屏验收时要在真实设备上操作；截图不能证明朗读顺序正确。

## 进入问题清单的条件

只有满足以下条件才创建问题项：工程已声明对应语言/主题/无障碍能力，且当前代码或运行证据表明目标形态存在具体缺口。问题项要写清页面、模式、现象、证据和验证方法，不能仅写“需要支持国际化/无障碍”。
