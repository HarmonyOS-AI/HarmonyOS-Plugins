## 第一原则：布局跟断点，`foldStatus` 只管折叠特性

这条规矩几乎能预防本域一半的缺陷。

**实测（HarmonyOS 6.0.2(22) foldable 模拟器）**：

| 形态 | 窗口尺寸 | 控件树字节数 |
|---|---|---|
| 折叠 | 1080×2504 | 86569 |
| 展开 | 2224×2496 | 196926 |
| **悬停** | **2224×2496** | **196926** |

悬停态与展开态在黑盒下**完全无法区分**——判定折叠态只有 `display.getFoldStatus()`
一条路——窗口尺寸、控件树都区分不了，只能问系统。

但反过来，**布局绝不能由 `foldStatus` 驱动**：

- `foldStatusChange` 触发时**窗口尺寸还没更新**，此时算布局会先按旧尺寸排一遍，
  随后 `windowSizeChange` 再排一遍——这就是开合时闪烁两次的根因
- 分屏、悬浮窗下窗口变了而折叠状态没变，靠 `foldStatus` 的布局根本不会响应

分工：**布局用断点 + `windowSizeChange`；业务状态快照与恢复用 `foldStatusChange`。**

同理不要用 `deviceType` / `isFoldable` 做布局分支——折叠屏的 `deviceType` 返回的也是
`'phone'`，按它分支会把展开态当手机处理。

## 折展状态检测

```typescript
if (display.isFoldable()) {           // 必须先判，否则非折叠设备上后续 API 返回 undefined
  const status = display.getFoldStatus();          // 首帧必须同步取一次，否则会闪切
  display.on('foldStatusChange', (s) => { /* ... */ });
}
```

`FoldStatus` 枚举（单折轴 3 种，双折轴 9 种）：

| 值 | 含义 |
|---|---|
| 0 | UNKNOWN |
| 1 | EXPANDED 展开 |
| 2 | FOLDED 折叠 |
| 3 | HALF_FOLDED 半折/悬停 |
| 11/21/12/22/13/23 | 双折轴组合态（`<主轴>_WITH_SECOND_<次轴>`） |

**双折轴设备（三折叠）必须处理 6 个组合态**，只判 1/2/3 会在三折设备上漏分支。

两个易混的枚举各管一件事：`FoldStatus` 管**折叠程度**，`FoldDisplayMode` 管**当前显示区域**。
需要知道"现在显示在哪块屏"用后者。直接用 SDK 枚举，不要手写同名常量。

`display.off('foldStatusChange', savedCallback)` 必须在 `aboutToDisappear()` 中调用，
且**要传回调引用**——裸 `off()` 会把其他组件注册的监听一起摘掉。

## 悬停态

### 判定条件是两个，不是一个

```typescript
const isHover = status === display.FoldStatus.FOLD_STATUS_HALF_FOLDED
                && isLandscape;   // 缺这个条件会在竖屏半折时误触发
```

只判折叠状态会导致竖屏半折（用户只是没完全打开）时错误进入悬停布局。

**只用 `pageWidth >= 600` 判多栏也识别不出悬停态**——悬停态的窗口宽度与展开态一样。

### 三条实现路径

| 方案 | 适用 | 代价 |
|---|---|---|
| `FolderStack` | 大多数场景：内容自然分上下半屏 | 最省事，可定制性最低 |
| `FoldSplitContainer` | 固定二/三分栏，各分区内容明确 | 需要配 `layoutOptions` |
| 自定义 | 复杂交互、需要自控旋转策略 | 要自己做折痕几何、方向管理、去抖 |

选 `FolderStack` 还是 `FoldSplitContainer` 看的是**分区会不会互相叠**：
`FolderStack` 是 `Stack` 模型，子组件可以叠在一起（视频铺满 + 控件浮在上层）；
`FoldSplitContainer` 是分栏模型，各区互不重叠（游戏画面 + 操作区）。

`FoldSplitContainer` 的分栏比例用 `PresetSplitRatio`，三个值来自 SDK：
`LAYOUT_1V1 = 1` / `LAYOUT_3V2 = 1.5` / `LAYOUT_2V3 = 0.6666666666666666`。
**这是比值不是百分比**，`LAYOUT_3V2` 表示前区 : 后区 = 3 : 2。

`FolderStack` 的两条**隐形杀手**约束：

- **不能包在 `if/else` 条件节点里** —— 包了会完全丧失悬停能力。
  需要条件显示时把它提到条件外，用其内部状态控制。
- **必须撑满全屏**（`width('100%')` + `height('100%')`），否则**静默退化成普通 `Stack`**，
  不报错、不生效。

`autoHalfFold` 让 FolderStack 自动响应系统半折叠状态，但它**不支持自定义悬停阈值**。
关掉它或走自定义实现时，**屏幕旋转必须自己管**——这是悬停适配最容易出错的部分。

### 方向决策基于折痕轴，不是视口宽高比

| 折痕方向 | 常态方向 | 悬停目标方向 | 为什么 |
|---|---|---|---|
| 横折痕（水平） | 竖屏 | 保持 `PORTRAIT` | 分屏本来就是上下，竖屏合理 |
| 竖折痕（垂直） | 竖屏 | 转 90° 到 `LANDSCAPE` | 原本的左右分屏要翻成上下分屏 |

只按 `rootWidth > rootHeight` 判，竖折痕设备在悬停态会保持左右分屏，完全错。

### 延迟调度，否则方向会抖

方向切换与布局刷新同时触发时，系统还没转完就收到了新的方向请求。官方经验值：
**进入悬停延迟约 120ms，退出约 220ms**，并对重复请求去重。

更根本的一条：**方向决策必须收敛到单一入口**。`onAreaChange`、`foldStatusChange`、
`foldDisplayModeChange` 各自调一次 `setPreferredOrientation` 就会互相覆盖，
表现为方向反复横跳。

## 折痕避让

### 几何来源

```typescript
const region = display.getCurrentFoldCreaseRegion();   // 非折叠设备返回 undefined
region.creaseRects;   // Array<Rect>，字段是 {left, top, width, height}
```

**三个坐标系陷阱**（折痕避让的实现最常踩）：

1. `creaseRects` 相对**屏幕**原点，控件 bounds 相对**窗口**原点 ——
   窗口非全屏时必须按 `windowRect` 偏移平移后再比较；页面根节点的 `globalPosition`
   偏移也要扣掉
2. `FoldCreaseRegion.Rect` 是 `{left, top, width, height}`，
   而 `AvoidArea` 与 UiTest 的 Rect 字段集不同，不能直接混用
3. 折痕坐标是 px，转换用 `uiContext.px2vp()`，**不是全局 `px2vp()`**

### 折痕方向要三级判定

**禁止只做一次 `width/height` 比较**——旋转过程中坐标转换会出现轴互换，单次比较会短时误判：

| 级别 | 判据 | 结论 |
|---|---|---|
| 一级 | 物理像素轴比 **1.35** | `height ≥ width × 1.35` → 竖折痕；`width ≥ height × 1.35` → 横折痕 |
| 二级 | 几何评分对比（阈值 **0.22**） | 轴比落在 1 ~ 1.35 之间（近方形）时，比较"直接评分"与"交换评分" |
| 三级 | 方向锁定 | 已知固定折痕轴的设备不因旋转改判 |

**方向锁定何时重置**：只在完全展开或完全折叠时重置。折叠过程中折痕数据会有微小
抖动，不锁定就会在中间态反复改判，布局跟着来回跳。

二级评分的参考权重（**未经实测校准**）：

```typescript
// 对候选方向各算一次，取分高者
score = coverageRatio * 2.2 - thicknessRatio * 3.2 - centerDistanceRatio * 0.35;
if (贴着容器上边或下边) score -= 0.5;   // 贴边的带更可能是安全区而非折痕
```

- `coverageRatio`：折痕带在**长轴方向**的跨度 ÷ 根容器该方向尺寸，上限 1.6。
  折痕总是横贯整屏，覆盖率高的那个方向才是它的走向。
- `thicknessRatio`：折痕带厚度 ÷ 根容器**垂直于该方向**的尺寸，上限 1。
  权重最大且为负——带越厚越不像折痕，这条同时兜住了异常数据。
- `centerDistanceRatio`：带中心到容器中心的距离 ÷ 半程。折痕基本居中。

> 参考实现的 `coverageRatio` 写成了 `rootWidthVp / rootWidthVp`，恒等于 1，
> 与它自己的文字描述不符，且只给了水平方向一个评分函数。上面按语义修正过。
> **这套权重只用来在近方形设备上给候选方向排序，不参与一级/三级判定**——
> 一级的 1.35 和三级的锁定是已过手的口径，不要用二级去覆盖它们。

### 折痕厚度必须钳位

折痕区域**不得超过屏幕对应维度的 35%**，超了就取折痕物理短边作安全高度
（参考实现取 **8vp** 作为该短边的估算值）。
少了这道保险，一次几何误算就会让避让区吃掉整个内容区——表现为悬停态黑屏、
布局只剩 `Blank`。

### 16vp / 40vp 是内容保护间距，不是分区锚点

- 上方内容底边距折痕上边界 **≥ 16vp**
- 下方内容顶边距折痕下边界 **≥ 40vp**

**分区的分界线始终以折痕的真实边界为准**，这两个数值加在分区**内部**。
把它们当成分界线偏移量，会让整个分区错位——这是折痕避让最高频的理解错误。

拿不到折痕数据时要有回退路径（按窗口中线切分并标注"未按真实折痕"），
而不是让布局崩掉。

## 开合连续性

形态切换时最常丢的三类状态，对应三种修法：

| 丢失项 | 根因 | 修法 |
|---|---|---|
| **页面跳回首页** | 形态切换触发 Ability 重建，路由栈用了组件默认初值 | `module.json5` 的 `configuration` 声明 `"screenSize"` `"orientation"` 自处理，改走 `onConfigurationUpdate`；同时保留当前路由 |
| **滚动位置丢失** | 列表重建后 offset 归零 | `List` 用 `scrollToIndex()` 按索引恢复；`WaterFlow` 用 `SLIDING_WINDOW` 模式；`Scroll` 手动记 offset 后 `scrollBy()` |
| **输入内容清空** | 内容只存在组件局部变量 | 提升到 Ability 级状态或持久化 |

**恢复索引从哪来**：滚动位置这条要成对做——`onScrollIndex()` 持续记录当前首个可见项
索引，切换后再 `scrollToIndex()` 恢复。只写恢复不写记录，"恢复到第几项"这个值无处可取，
是这条修法最常见的落地缺口。按**语义索引**恢复而不是按像素 offset：列数变了以后
像素 offset 对应的已经是另一条内容。

另外三条同样伤体验：

- **视频进度重置**：切换前快照进度与播放状态，恢复时用**序列号**防止旧的 `onPrepared`
  回调覆盖新状态；`autoPlay(true)` 会抢跑覆盖业务的暂停态，恢复逻辑必须可重入
- **图片变糊**：折叠态加载的低分辨率图直接拉到展开态。按断点切换图片资源，
  或开 `autoResize`，或预置多分辨率资源
- 开合后**不得引入额外操作步骤**（例如要求用户重新选一次）

#### 视频恢复要走双通道

`autoPlay(false)` + 两条触发路径，缺一条都有确定的失败场景：

| 通道 | 触发点 | 作用 |
|---|---|---|
| 1 | `onPrepared` 回调内 `setCurrentTime()` | 主路径，就绪即恢复；恢复后立刻清掉通道 2 的定时器 |
| 2 | 切换时启动的 ~500ms 定时器 | 兜底，防 `onPrepared` 延迟或丢失 |

四条反面模式，每条对应一个真实故障：

1. 不快照、指望 Video 内部状态自己保持 → 重建后进度归零
2. `autoPlay(true)` → 折展后从头播放，且会覆盖业务的暂停态
3. **只挂定时器不监听 `onPrepared`** → 定时器到点时 Video 可能尚未 prepared，
   `setCurrentTime()` 静默无效
4. 快照放在布局切换**之后** → 记录到的是切换后的状态，不是折展前的真实进度

无保存进度（首次加载）时才从头播放，别把它和"恢复失败"混成一个分支。
`aboutToDisappear` 里要清定时器。

### 回调时序：两个方向不一样

```
展开 → 折叠： foldStatusChange(半折) → foldStatusChange(折叠) → foldDisplayModeChange → windowSizeChange
折叠 → 展开： foldStatusChange(半折) → foldDisplayModeChange → windowSizeChange → foldStatusChange(展开)
```

注意**展开方向上 `foldStatusChange(展开)` 排在 `windowSizeChange` 之后**。
把"终态处理"挂在 `foldStatusChange` 上，两个方向的执行时机是不对称的——
需要终态语义时以 `windowSizeChange` 为准。

### 用 Visibility 而非 if/else 切换布局

`if/else` 销毁重建组件，会连带丢掉滚动位置与输入内容 —— 这是状态丢失最常见的间接原因。

## 内外屏与多段形态

判断当前在内屏还是外屏用**双通道**：`getFoldStatus()` 同步取初值 + `foldStatusChange`
跟变化（`FOLD_STATUS_FOLDED` 即外屏）。只监听不取初值会在首帧判错。

- 外屏往往是 `sm` 而内屏是 `md`，**外屏布局不能是内屏的等比缩小版**
- 阔折叠（如 Pura X）的外屏可能是**方形**，横向 sm 但纵向 md，
  按"竖屏"假设写的布局会失效
- **小方形屏空间紧张**，官方推荐上滑渐进隐藏标题栏与页签栏（渐进范围 100vp）、
  下滑以 300ms 动画恢复
- 三折叠 F/M/G 三种形态要分别有布局，且**必须落到断点上**，不要按形态硬编码

### 紧凑模式的判定阈值

判紧凑要用**换算后的 vp 宽度**，不要只凭折叠状态——同样是折叠态，直板折叠屏的外屏
是竖条，阔折叠的外屏是小方屏，两者能放的内容量差很多。

```typescript
const COMPACT_MAX_VP = 350;   // 布局判定阈值：窗口宽度 < 350vp 走紧凑布局
```

**这个阈值和任何设备的实测尺寸都不是一回事**，两者必须分开：设备实测值查
`device-matrix.md`，阈值是产品判定线。把某台设备的实测值直接当阈值用，换一台设备就会判错。

350 这条线之下同时包含阔折叠小方屏与直板折叠外屏——**这是有意的**，
两者都属于"一屏放不下常规布局"的紧凑档，走同一套收缩策略（页签左右化、标题栏缩字号、
搜索框收成图标）。如果业务需要把方屏与竖条外屏分开处理，不要去动这条阈值，
改为额外判高宽比：方屏的宽高比接近 1，竖条外屏明显小于 1。

折叠状态变化时必须重算——外屏切内屏后窗口宽度变了，紧凑标志不重算就会一直挂着。

具体机型的 vp 尺寸与断点见 `../references/device-matrix.md`。
